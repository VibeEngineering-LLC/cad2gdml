## 0. База аудита и метод

- **База:** коммит `edfe6f39611878368fa5df9da742bde667427665` (HEAD). Сборка для прогонов — `git archive HEAD` в каталог scratch, затем `dotnet build src\Cad2Gdml.Cli -c Release` (0 ошибок). Рабочее дерево во время аудита менялось другим исполнителем: `git diff` показывает незакоммиченную правку `src\Cad2Gdml.Core\Pipeline\Cad2GdmlPipeline.cs` (перехват IO/Format-исключений → код 2, проверка NaN до сшивки). Эта правка в аудит не входит; где она закрывает находку, это сказано (В2, В6). Тесты рабочего дерева и HEAD — 10/10.
- **Прогоны:** CLI `cad2gdml.exe` на входах, созданных мной в scratch `«локальный путь»` (ниже `$S`). Генератор сеток `$S\meshgen.py` (цилиндры/бруски/ступенчатое тело, запись bin/ASCII STL, OBJ, 3MF) написан локальной моделью через `gen_code.py` (ступень 2) по спеке `$S\spec_gen.md`; приёмка — объём цилиндра совпал с формулой многоугольника до 1e-12, перевёрнутая версия даёт минус тот же объём. Малые ручные входы — в `$S\err\`, `$S\in\`.
- **Шкала тяжести** (назначена мной, порогов нет): **блокер** — на штатном входе результат молча неверен либо GDML не загрузится у потребителя; **важно** — неверно на нестандартном, но реальном входе, либо нарушен контракт кодов/DESIGN, либо громкий отказ там, где вход годен; **мелочь** — гигиена, мёртвый/дублирующий код, косметика.
- Номера строк — по HEAD. «Доказано» = воспроизведено прогоном; «по чтению» = только код.

## 1. Блокеры

**Б1. GDML структурно невалиден для Geant4.** `src\Cad2Gdml.Core\Gdml\GdmlWriter.cs:510-512` пишет `<volume name=… materialref="…" solidref="…">` атрибутами; `:526` и `:534` — `<physvol ref="…"/>`. В GDML вещество и тело задаются дочерними `<materialref ref=…/>`, `<solidref ref=…/>`, а размещение — `<physvol><volumeref ref=…/><position…/></physvol>`. Эталоны на этой машине: `«локальный путь»` (volume с дочерними materialref/solidref) и `:173-176` (physvol с volumeref/positionref); спека задачи `tasks\t\T16.md` тоже говорит «with materialref, solidref» без уточнения формы. Воспроизведение: `cad2gdml.exe $S\err\crystal_dot.obj --unit mm --front +z --allow-default-material --out $S\out\x` → в `<structure>` строка `<volume name="crystal" materialref="NaI" solidref="crystal_2">`. Загрузку в Geant4 я не запускал (нет прогона); вывод опирается на формат GDML и эталонные файлы. Тесты этого не ловят: ни один тест не читает GDML (см. В17).

**Б2. Размещение (position) нигде не пишется; примитивы стоят в начале координат.** `GdmlWriter.cs:399-435` (box/tube/polycone) и `:524-528` (`physvol` без позиции); `<position>` встречается только в `<define>` для вершин tessellated (`:324`). Поля `SolidShape.X0/Y0` (box — ещё центр по z) выставляются в `RevolutionRecognizer.cs:229-230`, `BoxRecognizer.cs:91-93`, но нигде не читаются (grep `X0|Y0` по src: только присвоения). Для tube/box координата центра и смещение оси потеряны; у polycone теряется только смещение x,y. Доказано: сцена `$S\in\A` (кристалл 6-угольник → tessellated, вершины в кадре z∈[-50.8; 0]; вода-образец → tube): образец в кадре занимает z∈[9.2; 49.2] (тот же сдвиг, что у кристалла), а в GDML — `<tube … z="40">` без позиции, то есть z∈[-20; 20]; ошибка 29.2 мм по оси. Для кристалла-tube (`in\A` с n=64) он окажется центрированным в нуле вместо [-50.8; 0] — детектор и источник пересекаются. Тот же дефект уводит `SketchBuilder` (рисует по Z0/Z1) от GDML.

**Б3. Единицы 3MF игнорируются.** `ThreeMfImporter.cs:36-50` вычисляет `unitToMm` (из атрибута `unit` или из `--unit`), дальше значение нигде не используется: `ResolveObject` (`:306-355`) и `BuildMeshFromElement` (`:358-421`) строят вершины без масштаба. Доказано: `$S\in\A\crystal_cm.3mf` (`unit="centimeter"`, радиус 2.54) → `<tube … rmax="2.54" z="5.08">`, ожидалось 25.4 и 50.8 мм. Ключ `--unit cm` на 3MF тоже без эффекта (3MF в мм + `--unit cm` → rmax 25.4), при этом STL того же запуска масштабируется (вода ×10 → rmax 300). Молчаливая ошибка в 10/1000/25.4 раза.

**Б4. `Eigen3.Jacobi` считает неверно → ось кристалла определяется ненадёжно.** `src\Cad2Gdml.Core\Meshes\Eigen3.cs:87` — в обновлении диагонали знак `- s*s*aqq` (должно быть `+`), след матрицы не сохраняется (также см. угол `:73`). Доказано числом: тензор `diag(1,2,5)` повёрнутый на 0.5 рад вокруг z → собственные значения `0.894; 1.292; 5`, сумма 7.19 вместо 8; тензор `diag(2,2,1)` повёрнутый на 30° вокруг x → `-0.125; 1.25; 2` (отрицательное для положительно определённой матрицы), ось `(0; 0.5; 0.866)` вместо `±(0; -0.5; 0.866)`. Следствие в конвейере: цикл Якоби запускается, как только внедиагональная сумма превышает 1e-14 от диагонали, а шум float32 это обеспечивает. Доказано прогоном: цилиндр r=25.4 h=50.8 n=64 со сдвигом центра (0,0) → код 0, tube; со сдвигом (100,100) мм → `E_AXIS_AMBIG`, код 4; r=30 h=10 со сдвигом 100 → код 4; r=10 h=60 со сдвигом 100 → код 0 (повезло: запасной путь «самое длинное ребро bbox»). Наклонённый на 30° кристалл (`$S\in\F`) → код 4. Запасной путь (`FrameBuilder.cs:219-248`) для диска r=30 h=10 даёт ничью ex=ey → отказ, для вытянутого тела по оси файла — верный ответ случайно.

**Б5. Ориентация кадра: +z не всегда от кристалла к источнику.** `FrameBuilder.cs:48` берёт `zF = axisDir` (знак собственного вектора), а `:138` выбирает передний торец независимо; нулевая плоскость ставится на выбранный торец (`:60-68`). Если передний торец — тот, что в сторону `-zF`, кристалл оказывается в z∈[0; +L], источник в отрицательных z — вопреки DESIGN §3.2 («+z — от кристалла к источнику», иначе gdml2in даёт `E_ORIENT`). Доказано: `$S\in\A` (источник над кристаллом в файле) → вершины кристалла z∈[-50.8; 0] (верно); `$S\in\B` (источник под кристаллом, z∈[-60;-20]) → z∈[0; +50.8] (неверно, сцена перевёрнута). Код 0, предупреждения нет. Ориентация «лицом к −Z» (как в `RC110_detector.gdml`, шапка) — штатный случай.

**Б6. Центр и торцы кристалла считаются по среднему вершин, а не по протяжённости.** `FrameBuilder.cs:34` (`ComputeCentroid` = среднее вершин, `:194-204`) + `:35-38` (`halfLen` — полупротяжённость). При неравномерной раскладке вершин вдоль оси (фаска, проточка, лишнее кольцо) торцы смещаются. Доказано: цилиндр r=25.4 h=50.8 с дополнительным кольцом вершин на z=15 (`$S\in\C`) → polycone с `zplane z=-44.0701 … 6.7299` вместо `-50.8 … 0`: плоскость переднего торца не в z=0, ошибка 6.73 мм, код 0.

## 2. Важные

**В1. OBJ: `0,5` читается как 5 (молчаливый масштаб).** `ObjImporter.cs:109-111,137`: `double.Parse(s, CultureInfo.InvariantCulture)` использует `NumberStyles.Float | AllowThousands`, запятая — разделитель тысяч и просто отбрасывается. Доказано: `$S\err\crystal_ru.obj` (вершины ±0,5×±0,5×±1) → `<box x="10" y="10" z="2">`; тот же файл с точкой → `x="1" y="1" z="2"`, оба раза код 0. Те же вызовы в `ThreeMfImporter.cs:284-295,378-380,403-405` (в XML запятая в числе — нарушение формата, но принимается). STL использует `NumberStyles.Float` (`StlImporter.cs:212-214`) и этому не подвержен; `MiniJson` защищён собственной грамматикой (`:154-185`).

**В2. Код выхода: битый/отсутствующий вход → 9 (E_INTERNAL), а не 2; итоговая строка называет не тот ID.** Все исключения импортёров перехватывает единый `catch` (`Cad2GdmlPipeline.cs:85-90`) → 9. Доказано: несуществующий файл, пустой файл (0 байт), мусорный файл, ASCII STL без треугольников, STL с лишними 2 байтами после бинарного тела, OBJ с индексом грани за пределами вершин (`$S\err\crystal_bad.obj`), STL с `1e999` (OverflowException — ловится только FormatException, `StlImporter.cs:216`), несуществующий `--materials` — все `rc=9`, тогда как DESIGN §10.1 относит их к коду 2. `Program.cs:146-150` возвращает 1 — недостижимо, потому что `Run` ловит всё; 1 вне допустимого набора. Итоговая строка (`Program.cs:224-238`) выбирает ID по коду, а не по диагностике: `E_UNIT_MISSING` → «код 2 E_FORMAT»; `E_AXIS_AMBIG`/`E_ROLE_AMBIG`/`E_FRONT_AMBIG` → «код 4 E_ROLE_NONE»; код 9 → `E_UNKNOWN`. Незакоммиченная правка Pipeline переводит IOException/FormatException/InvalidData в 2; ID итоговой строки она не меняет.

**В3. Нет проверок замкнутости-ориентации, нулевого объёма, пустого тела.** `Cad2GdmlPipeline.cs:194-199` учитывает только `OpenEdges`; `MeshTopology` считает `NonManifoldEdges` и `InconsistentEdges` (`MeshTopology.cs:85-101`), но никто их не читает (DESIGN §4.4: `E_MESH_NONMANIFOLD`/`E_MESH_ORIENT`, код 3; «мало граней < 4»). Доказано: (а) в образце `water_flip1.stl` один треугольник перевёрнут → код 0, объём 111.74 см³ вместо 112.92 (−1 %), GDML с несогласованной обмоткой; та же ошибка в кристалле даёт ложный `E_AXIS_AMBIG` (код 4) вместо кода 3; (б) двусторонний «листок» (`$S\in\sheet.stl`, объём 0) → код 0, `<tessellated>` нулевого объёма; (в) STL из одного вырожденного треугольника (`$S\in\plug.stl`) → код 0 и в GDML пустой `<tessellated name="plug_2"></tessellated>` без граней (Geant4 такое не принимает), в `<define>` остаётся одна лишняя `position` (`GdmlWriter.cs:316-330` выводит и неиспользуемые вершины).

**В4. Открытая сетка некритичной детали молча исключается из сцены.** `Cad2GdmlPipeline.cs:246-247`: деталь удаляется с предупреждением, код 0. DESIGN §4.4: открытая деталь — `E_MESH_OPEN` (код 3), выкидывание — только по ключу `--drop-open`. Доказано: `$S\in\H\lead_shield.stl` (свинцовая защита с одним удалённым треугольником) → код 0, в GDML защиты нет (`grep -c lead_shield` = 0). Для расчёта защиты это существенная потеря.

**В5. ASCII STL: нераспознанная вершина молча пропускается, ломая группировку по три.** `StlImporter.cs:195-219`: строка `vertex` с числом в запятой/мусором (`FormatException`) или менее чем с тремя токенами пропускается через `continue`, счётчик `slot` сдвигается, все последующие треугольники составляются из чужих вершин. Доказано: `$S\in\A\water_comma.stl` (одна координата `27,716386`) → код 3 «Открытая сетка» (ложная причина вместо «ошибка формата»); `crystal_comma.stl` (4 вершины) → код 4. Усечённый треугольник в конце (1–2 вершины) тоже теряется без сообщения. Также: несколько `solid` в одном файле сливаются в одну деталь (`:164-242`).

**В6. NaN/∞ проходят до записи.** HEAD без проверки: `double.Parse("NaN")` принимается (net48), в бинарном STL float NaN читается как есть. Доказано: OBJ-тетраэдр `water_nan.obj` как источник → код 0, в GDML `<position name="v1_3" x="NaN" y="NaN" z="NaN">` (NaN расползается по всем координатам через матрицу кадра). Если NaN в кристалле, итог — `E_AXIS_AMBIG` (код 4, «рёбра bbox близки») вместо причины. Незакоммиченный `E_MESH_NAN` (в рабочем дереве, `ProcessMeshes`) закрывает это для обоих форматов; в HEAD — нет. Целочисленное переполнение при сшивке: `MeshWelder` (`Mesh.cs:185-187`) приводит `Math.Floor(v·1e5)` к `int`; при |координате| > 21 474 мм приведение не определено, все такие вершины попадают в одну ячейку (замер: цилиндр 8000 сегментов со сдвигом 30 000 мм — 0.78 с против 0.29 с без сдвига; рост квадратичный по числу вершин; на миллионе вершин зависание вероятно, не проверено).

**В7. Ключ `--crystal` не побеждает регулярку роли.** `RoleAssigner.cs:26-36` помечает названную деталь кристаллом, но цикл `:39-54` пропускает (`continue`) только её саму; любая другая деталь, имя которой содержит `nai|csi|labr|…|scint|crystal` (подстроки, `RoleOptions.CrystalRegex` `:9`), тоже становится кристаллом. Доказано: `--crystal detector_main` при наличии `csi_extra.stl` → `E_ROLE_AMBIG`, код 4. Подстроки дают ложные срабатывания (`nai` в «rainbow/…», `pb` в «…pbox», `case` в «showcase»), по-русски `кювет` → Container, но см. В8.

**В8. Вещества по умолчанию подбираются подстрокой и дают физически неверный ответ молча.** `MaterialLibrary.cs:76-81`: `crystal|nai|scint|кристалл` → `NaI` для ЛЮБОГО «crystal» (LaBr₃, BGO, CsI-кристалл получат NaI, `W_MAT_DEFAULT` не выдаётся, это «правило»); `cu|copper|медь` → `G4_Cu` по подстроке «cu» (кювета/Cuvette, accumulator, circuit); `air` → `G4_AIR` по «chair/repair/stair»; `lead|pb` — «leadscrew», «pbs». Правило первого совпадения без `W_MAT_CONFLICT` (DESIGN §5). Плотность NaI 3.67 против `G4_SODIUM_IODIDE` 3.667 из DESIGN §5. В окне `AllowDefaultMaterial = true` зашит (`MainForm.cs:292`), в нём всё неопознанное молча становится воздухом (с предупреждением только в тексте).

**В9. Файл веществ: схема не совпадает с DESIGN §5; неизвестное вещество не ловится; нулевая плотность пишется.** `MaterialLibrary.cs:147-160` читает `custom.<имя>.density` и `.elements{символ: доля}`; DESIGN §5 описывает `density_g_cm3` и `fractions` парами `[ссылка, доля]`. Доказано: `$S\in\mat_design.json` (по схеме DESIGN) → `<D value="0" unit="g/cm3"/>` без единой `<fraction>` и код 0 (Geant4 отвергнет плотность 0). `E_MAT_UNKNOWN` (код 5) не реализован: правило, ведущее на `G4_WATR` (опечатка), → `materialref="G4_WATR"`, код 0; `GdmlWriter.cs:263-264,356-357` просто пропускает `def == null`. Неизвестный символ элемента отбрасывается молча (`:347-350`) — получится `<fraction ref="X">` на неопределённый элемент. Доли не нормируются и сумма не проверяется (DESIGN §7.2 `W_FRACTION_SUM`). Регистр: `Find` нечувствителен к регистру (`:36`), `materialref` пишется в исходном (`GdmlWriter.cs:511` берёт `p.Material`), `<material name>` — из определения (`:360`): при несовпадении регистра ссылка висячая. Вне JSON-ветки: если корень JSON не объект — молча подменяется встроенной библиотекой (`:122`). `<element name Z A>` (`GdmlWriter.cs:342-344`): в схеме GDML масса задаётся дочерним `<atom value=…/>`; образцов `<element>` на машине не нашёл — по памяти схемы, не проверено.

**В10. Роли в GDML не читаются gdml2in.** `GdmlWriter.cs:514-515` пишет `auxtype="Cad2Gdml:Role" auxvalue="Crystal"` (значение — `PartRole.ToString()`); DESIGN §6 требует для crystal/source/vessel `BecqMoni:Role` и строчные значения (`crystal`, `source`, `vessel`), плюс `Cad2Gdml:SourceName`. `PartRole` (`SceneModel.cs:9-17`) не содержит Reflector/Headspace/Window; имена объёмов не `LV_<SafeName>` (`GdmlWriter.cs:250-252`: объём и тело получают `Name` и `Name_2`). Дополнительно активный объём источника `PV_LV_…` отсутствует.

**В11. Числа и имена GDML расходятся с DESIGN §7.2–§7.4.** `Fmt` (`GdmlWriter.cs:185-189`) = `G9`, DESIGN — `Math.Round(v,6)`/`0.######`. Доказано: в выводе `y="3.11060293E-15"` (шум от матрицы кадра), `x="-25.3999996"`, `rmax="30.0000008"` и `rmax="25.400001"` (шум float32); `aunit="rad"` и `deltaphi="6.28318531"` вместо `deg`/`360`. Имена: `GdmlName.Transliterate` (`:54-75`) оставляет любые буквы Unicode (`IsLetterOrDigit`): доказано `Ωmega_äö` попал в имена volume (`$S\in\N`); подстрока `0x` не обрабатывается (`p0x1F_sample`); обрезки до 64 знаков нет. Сочетание с E-нотацией и не-ASCII — риск для парсера Geant4 (CLHEP-выражения), не проверено.

**В12. `--front ±z` задаёт только направление по Z файла.** `FrameBuilder.cs:128-135`: если ось кристалла перпендикулярна Z файла (`|dz| < 1e-9`) → `E_FRONT_AMBIG`; `Program.cs:120` не принимает `±x`/`±y`. Доказано: `$S\in\Y` (ось по Y) с `--front +z` и `-z` → код 4; без ключа (источник есть) → код 0. Боевой случай из DESIGN §3.1 — «ось прибора — Y сетки», у детектора без источника выбрать торец вручную нельзя вовсе.

**В13. Распознавание тел вращения: нерегулярные, но корректные тела уходят в tessellated; для кристалла «tube» не гарантирован.** `RevolutionRecognizer.cs:36-40` берёт ось по центру bbox, а не по оси/центру масс (DESIGN §4.1 п.1).
