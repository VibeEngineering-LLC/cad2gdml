## Блокеры

### B-01. Неманифольд понижен до предупреждения, неверная ориентация одного из касающихся тел уходит в GDML молча (код 0)
- `src\Cad2Gdml.Core\Pipeline\Cad2GdmlPipeline.cs:282` (W_MESH_NONMANIFOLD вместо E_MESH_NONMANIFOLD); знак объёма берётся по сумме всей сетки, `:312-318` (FlipWinding по `vol < 0`); `MeshTopology.Analyze` не считает «несогласованность» на рёбрах с более чем 2 гранями (`Meshes\MeshTopology.cs:93`, ветка `total > 2` не доходит до проверки `Forward == 2`).
- Воспроизведение: `crystal.stl` = куб 20×20×80 плюс вывернутый (нормали внутрь) брусок 10×10×80, делящий с ним ребро целиком (вершины общие) + `water_sample.stl` (куб 30). Файлы: `sc\u3\`. Команда: `cad2gdml sc\u3\crystal.stl sc\u3\water_sample.stl --out o\u3 --unit mm --allow-default-material`.
- Результат: код 0, единственное предупреждение `W_MESH_NONMANIFOLD ... 1`. Сумма знаковых объёмов треугольников кристалла в GDML 24000 мм³; при нормалях наружу должно быть 32000 + 8000 = 40000: малое тело вошло с минусом (−8000). Проверено разбором `<triangular>` в `o\u3\crystal.gdml`. Касание в одной вершине (`sc\t5\`, куб 20 мм и вывернутый куб 6 мм): сумма по GDML (кристалл + образец-бокс) 34784 вместо 35216, предупреждений нет (это дефект и прежней версии: рёбер >2 нет, ошибки по неманифольду не было, но «исправить» его разбивка тоже не может, так как связность считается по вершинам).
- По диффу (удалённые строки `E_MESH_NONMANIFOLD`, `return false`; сборку v0.3 не запускал) раньше такая сетка давала E_MESH_NONMANIFOLD, код 3. Теперь Geant4 получит тело с обращённой нормалью.
- Соседний случай: равные тела с общим ребром, одно вывернуто (`sc\u2\`) → W_MESH_NONMANIFOLD + `E_MESH_EMPTY` «Объём < 1e-6» (код 3): сообщение причину не называет.
- Что нужно: ориентацию проверять покомпонентно (после разбиения по рёбрам, а не по вершинам) либо оставить неманифольд ошибкой, пока не проверена ориентация каждого тела.

### I-01. Разбивка меняет смысл входа: деталь «crystal» из нескольких тел даёт E_ROLE_AMBIG (код 4), обхода нет

### I-04. GUI-тест `gui_convert_twice` проверяет другой путь, чем рабочий, а «красный» вылечен удлинением ожидания
- Коммит `3fc3128`: `ChecksGui.cs:150` ожидание после включения кнопки 25 → 250 итераций по 20 мс (0,5 → 5 с) на каждый из двух прогонов.

Вся «лестница» — межпоточные SendMessage к циклу `DoEvents`.
- Значит: (а) тест не проверяет путь UI-потока, на котором работает приложение; (б) окно 5,3 с скроет реальную позднюю установку картинки/статуса до 5 с; (в) проверки слабые: статус только «не начинается с Сбой», `t2 < t1` пропускает «PNG не обновлён» при равенстве (`ChecksGui.cs:108`).
- Дополнительно: на новые функции тестов нет вообще — `grep` по `src\Cad2Gdml.Tests` на I_SPLIT, KeepOpen, E_SCENE_EMPTY, W_MESH_NONMANIFOLD, W_COMPONENT_TINY, NoSplit даёт 0 совпадений. Изменён один существующий тест (`no_crystal`: ожидание кода 4 → 0).
- Время отклика формы в рабочем режиме (поток UI) не измерено: мой пробник с ручной установкой WindowsForms-контекста не подтвердил смену контекста (печатается базовый тип), поэтому цифры выше относятся только к тестовому пути. Конвейер сам идёт в BackgroundWorker: простой цикла `DoEvents` ≤ 37 мс на всех прогонах.

Имена кусков: `_c01` получает деталь с наибольшим числом треугольников, а не объёма (у равных — по порядку вершин, `:340-355`); при >99 кусках порядок `SortParts` ordinal даёт `c1079` перед `c108` (`o\det1\many.gdml`); нумерация с пропусками после отброшенных мелких; если остался один кусок, он всё равно переименован `_c01` и в журнале «разбита на 2 связных тел»; возможен конфликт с уже существующим именем `x_c01.stl`.
